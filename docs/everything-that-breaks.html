Everything that breaks when you sandbox a terminal

Nine of them. Each one measured, with what it looks like, why it happens, and what fixes it.

July 2026. Companion to the debugging write-up, which tells the story of finding the first one. This page is the catalogue.

The received wisdom for getting host access out of a Flatpak is flatpak-spawn --host, and for a terminal emulator that means overriding the shell command. It works: the shell really does run on your real system. It is also, on its own, nowhere near enough — and the gap is invisible, because the terminal looks fine.

What follows is everything that turned out to be broken, found by measuring rather than guessing. The useful structure isn't the order they were found in; it is where the state lives, because that determines how each one fails and whether it can be fixed at all.

State in the kernel

These are the hard ones, because kernel objects are global and single-owner. They do not respect the two-process-tree split that flatpak-spawn creates, and no amount of configuration will make them.

1. The controlling terminal goes to the wrong process

Symptom: bash: cannot set terminal process group (-1), no job control in this shell. Ctrl+Z, fg, bg and jobs all silently do nothing.

TIOCSCTTY is an exclusive, one-shot claim: the first session to grab a PTY owns it permanently. Alacritty does the textbook thing — setsid() + TIOCSCTTY in its child, then exec — but under Flatpak that child is flatpak-spawn, a proxy that only makes a D-Bus call. The proxy performs the land grab; the real shell is spawned separately by the portal and arrives to find the terminal taken.

flatpak-spawn --host bash -l   pts/0  Ssl+    <- proxy owns the terminal
bash -l                        ?      Ss      <- the actual shell, tty_nr = 0

Fix: a relay that opens a second PTY and deliberately never claims it. The portal's own child setup then hands it to the shell automatically. Nothing needs to be built to acquire the terminal — something needs to stop stealing it. Full story here.

2. SIGWINCH is never forwarded

Symptom: zoom in and the text near the cursor smears while the rest of the screen looks fine. Running programs never learn the terminal resized.

flatpak-spawn blocks and forwards eight signals — visible in its own signal mask, SigBlk: 00000000000a4a07 = HUP INT QUIT USR1 USR2 TERM CONT TSTP. SIGWINCH is not among them, so the kernel delivers it to the proxy and it goes in the bin.

The smearing is worth understanding: readline doesn't repaint the screen, it repaints its own region using the width it still believes in. One band of the terminal gets rewritten against stale geometry while everything around it already reflowed. It reads as "the zoom is centred on part of the screen." It isn't centred on anything.

Fix: the relay is the foreground process group of the outer PTY, so it does receive SIGWINCH, and copies the size across.

3. Every window has the same PID

Symptom: the second window opened from the desktop shows Unable to create socket: AddrInUse and Unable to create log file: File exists.

Alacritty names its IPC socket and log file after its own process ID — a fine unique key everywhere except here. Every flatpak run gets a fresh PID namespace, so every instance is PID 2:

host PID 2129727:  NSpid: 2129727   2
host PID 2129960:  NSpid: 2129960   2
host PID 2130588:  NSpid: 2130588   2

The runtime directory and /tmp are shared per application, not per instance — which is exactly why alacritty msg can reach across instances at all — so the first instance wins both names and every one after it collides. The banner is cosmetic; the consequence is that those instances have no IPC socket at all, so msg from their windows drives whichever instance won the race.

Fix: /.flatpak-info carries an instance-id that genuinely is unique. Use that instead of a PID that isn't.

State in the environment

4. The portal launders TERM away

Symptom: no colour anywhere, and every ncurses program failing.

tput colors: tput: No value for $TERM and no -T specified
infocmp:     FAILS
clear:       TERM environment variable not set.
less:        tput: No value for $TERM and no -T specified

flatpak-spawn --host does not hand the sandbox's environment to the host process; the portal starts host processes from the host session's environment. Traced across the boundary:

relay          (sandbox)   TERM=alacritty
flatpak-spawn  (sandbox)   TERM=alacritty
bash -l        (host)      TERM=<UNSET>

This laundering is a feature, and the reason this fix has to be narrow. It strips LD_LIBRARY_PATH, XDG_CONFIG_HOME, GI_TYPELIB_PATH and container=flatpak — without it, host programs would start reading the runtime's configuration. The casualty is that a terminal's identity is legitimately sandbox-side information that has to cross.

Fix: an explicit --env allowlist — TERM, COLORTERM, and later ALACRITTY_SOCKET. An allowlist, never a bulk forward.

State on the host filesystem

5. terminfo is unreachable

Symptom: none, until someone installs on a host that has never heard of your terminal — then every ncurses program fails again despite TERM being set correctly.

A TERM value only means something if the host has a matching terminfo entry, and a sandboxed app cannot write to the host filesystem to install one. alacritty-direct is already missing on the machine this was developed on.

Fix: a host-side bootstrap that checks and degrades. This is the one category with no clean answer — only graceful failure.

announced alacritty            -> alacritty        256 colours
announced alacritty-direct     -> xterm-256color   256 colours
announced totally-made-up-term -> xterm-256color   256 colours

It is also why Ptyxis announces xterm-256color: VTE's terminfo is universally present, so it sidesteps the problem entirely by never needing a host-side file.

7. The alacritty binary isn't on the host

Symptom: alacritty msg create-window at your own prompt returns command not found.

The shell runs on the host; the binary lives inside the Flatpak. The IPC it wants is running perfectly well — nothing is wrong with the socket. Re-entering the Flatpak is enough, because a second instance shares the first's runtime directory and finds the socket by itself.

Fix: ship a shim on a host-visible path. The sandbox learns its own host-side location from app-path in /.flatpak-info, and the relay appends that directory to PATH host-side — appended, so a natively installed Alacritty still wins.

State in the PID namespace

6. The shell is invisible, so "new window here" fails

Symptom: every new window opens in $HOME, wherever you actually were.

Alacritty finds the current directory by reading /proc/<tcgetpgrp(pty)>/cwd. The sandbox sees five processes; the host has 491, and the shell is not among them.

I wrote this one off as unfixable — it wants OSC 7, and Alacritty's documented escape support is OSC 0, 1, 2, 4, 8, 10, 11, 12, 50, 52, 104, 110–112, with no 7 anywhere. That was wrong, and instructively so. Alacritty is not reading the shell's cwd. It reads the cwd of whatever holds the foreground process group of its own PTY — the relay, on our side of the boundary. And the shell already announces its directory in-band, where the relay sees every byte.

relay cwd at start        : /home/me
relay cwd after shell cd  : /home/me/zz-marker-dir
relay cwd after second cd : /home/me/my-progs

Fix: the relay follows OSC 7 and OSC 3008 reports and chdir()s to match. Alacritty's existing lookup then returns the right answer, unchanged. Note the symmetry with #3 — the same namespace makes a PID invisible here and non-unique there.

Not the sandbox's fault

8. flatpak run <app-id> was a trap

With no arguments it bypassed the shipped config entirely and dropped you into a shell trapped inside the runtime — the exact failure the package exists to prevent, reachable by the most obvious command anyone would type. A packaging mistake, not a platform one. The launcher now supplies the config when the caller didn't.

9. Ctrl+scroll doesn't zoom

Alacritty's entire default mouse binding table is three lines: right click, Ctrl+right click, middle click. WheelUp/WheelDown are perfectly bindable and upstream simply doesn't bind them — the ability to bind them at all only landed in December 2025, after seven years of requests. Nothing to do with sandboxing; every Alacritty user has this.

It is worth stating plainly because it was reported to me as "zoom is broken in the Flatpak," and the obvious move was to assume the sandbox. Two of the three zoom complaints were the sandbox. This one wasn't. Only measuring told them apart.

Diagnostics worth stealing

Most of these generalise to any app that spawns host processes from a sandbox.

# Does a process have a controlling terminal? Field 7 of stat; 0 = none.
awk '{print $7}' /proc/<pid>/stat

# Who holds it instead? Look for Ss+ on a pts.
ps -eo pid,ppid,tty,stat,args | grep flatpak-spawn

# Which signals does the proxy actually forward?
grep SigBlk /proc/<flatpak-spawn-pid>/status

# Is the sandbox's devpts a separate instance from the host's?
grep devpts /proc/self/mountinfo
flatpak run --command=sh <app-id> -c 'grep devpts /proc/self/mountinfo'

# What PID does a sandboxed process think it has?
grep NSpid /proc/<pid>/status

# What does the sandbox know about its own host-side paths?
flatpak run --command=cat <app-id> /.flatpak-info

And one that saved a lot of time: Alacritty's own IPC exercises font rasterisation, grid reflow, TIOCSWINSZ and SIGWINCH-across-the-boundary in a single command, with no key injection needed.

flatpak run --command=alacritty <app-id> msg config 'font.size=30'

The pattern

Every boundary above is drawn correctly. None of this is a Flatpak bug. It is that a terminal has state which legitimately must cross a boundary built to stop state crossing — and that state lives in four different places, each of which fails differently.

The other thing worth taking away is a debugging habit. Twice I concluded something was unfixable, and twice the answer was already sitting on my own side of the boundary: read the relay's /proc entry rather than the shell's; read app-path rather than trying to reach the host. Both times the instinct was to build machinery to reach across.

When a sandbox hides something, don't ask how to reach across. Ask what on your side already knows.
